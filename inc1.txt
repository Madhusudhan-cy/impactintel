## 3. Code Knowledge Graph

The Code Knowledge Graph represents the structural relationships inside a software repository.

### Node types

Initially, our graph schema should support these conceptual node types:

- File
- Function
- Class
- Component
- API Route
- Test

Not every node type needs a complete extractor in Increment 1.

### Relationship types

The planned relationship types are:

- `imports`
- `defines`
- `calls`
- `renders`
- `exposes`
- `handled_by`
- `fetches`
- `tests`

The first increment should focus primarily on:

- File nodes.
- Import relationships between files.

Design the schema so that other node and relationship types can be added later without redesigning the entire system.

## 4. Critical graph direction rule

This is one of the most important architectural decisions.

Represent dependency relationships as:

**Caller / Dependent → Dependency**

For example:

`Checkout.js → PaymentService.js`

`PaymentService.js → Database.js`

This means:

- Checkout depends on PaymentService.
- PaymentService depends on Database.

If Database changes, we need to identify its dependents.

Therefore, we must traverse the graph backwards.

Example:

<escape>
Checkout.js → PaymentService.js → Database.js
</escape>

If `Database.js` changes, reverse traversal should identify:

- Directly affected: PaymentService.js
- Indirectly affected: Checkout.js

This is called reverse dependency traversal.

Do not reverse the graph's stored edge direction. Keep the original dependency direction and traverse incoming edges when calculating impact.

### Module 5: Reverse Dependency Impact Analysis

Implement an impact-analysis function.

Conceptual function:

```python
def find_affected_components(
    graph,
    changed_files,
    max_depth=3
):
    ...
```

Input:

- Graph.
- One or more changed files.
- Maximum dependency traversal depth.

Output:

- Changed files.
- Directly affected files.
- Indirectly affected files.
- Dependency depth.
- Dependency path or paths.
- Supporting edge evidence.

Rules:

1. Start from the changed file.
2. Find files that directly depend on it.
3. Continue traversing incoming dependency relationships.
4. Stop after three dependency levels.
5. Do not include the changed file itself in the affected-components list.
6. Do not include unrelated files.
7. Return the closest affected files first.
8. Support multiple changed files.
9. Handle cycles without infinite loops.
10. Preserve the dependency path explaining why each file is considered affected.

Example:

Stored graph:

```text
app.js → paymentRoutes.js
paymentRoutes.js → paymentService.js
paymentService.js → database.js
paymentService.js → logger.js
```

If `database.js` changes, expected results:

```text
Changed:
database.js

Directly affected:
paymentService.js

Indirectly affected:
paymentRoutes.js
app.js
```

`logger.js` must not be marked affected by this change because it is a dependency of paymentService.js, not a dependent of database.js.

This distinction is important.

### Module 6: Impact Depth Rules

Use the following initial rule:

- Maximum three dependency levels.
- Changed file is depth 0.
- Direct dependents are depth 1.
- Their dependents are depth 2.
- Continue up to depth 3.

Tests will be handled as a special relationship type in a future increment. Do not let test relationships consume the three-level dependency traversal limit when that functionality is added.

For Increment 1, focus on file import relationships.

4. A changed file with no dependents.
5. A dependency chain longer than three levels.
6. Multiple changed files.
7. Circular dependency relationships.
8. An unrelated file that must not appear in the impact results.
9. Correct dependency direction.
10. Correct dependency path reporting.

Tests must verify actual results, not just whether functions execute without errors.
