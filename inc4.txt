# PART 2: OBJECTIVE OF INCREMENT 4

## 1. What are we building?

We are adding a conversational interface that allows developers and reviewers to ask natural-language questions about their connected GitHub repositories.

Examples:

- What does `process_payment()` do?
- Which functions call `process_payment()`?
- Which components depend on PaymentService?
- Explain the payment architecture.
- Where is payment failure handled?
- What happens when a user logs in?
- Which API route handles payment requests?
- What tests are related to payment validation?

**Retrieve the right code, understand its structural relationships, generate an evidence-grounded explanation, and verify important claims before returning the answer.**

Our RAG architecture consists of:

1. Query understanding.
2. Graph RAG retrieval.
3. BM25 keyword retrieval.
4. Vector similarity retrieval.
5. Hybrid result fusion.
6. Optional reranking.
7. LLM answer generation.
8. Evidence-based claim verification.
9. LangGraph workflow orchestration.

## 6. Implement Graph RAG

Reuse the existing Code Knowledge Graph.

Graph RAG retrieves structural repository context.

It should support questions such as:

- Which components depend on this module?

### Retrieval workflow

1. Identify relevant code entities from the query.
2. Locate their graph nodes.
3. Traverse relevant relationships.
4. Retrieve connected nodes.
5. Retrieve relationship evidence.
6. Retrieve source-code chunks for the selected nodes.

- imports
- defines
- calls
- renders
- exposes
- handled_by
- fetches
- tests

Respect graph direction.

Stored dependency relationships follow:

`Dependent → Dependency`

For queries asking who depends on an entity, use reverse traversal.

For queries asking what an entity depends on, follow outgoing dependency relationships.

Do not confuse these two directions.

Graph RAG must preserve:

- Relationship type.
- Source node.
- Target node.
- File path.
- Line number where available.
- Evidence.
- Confidence.

Do not invent graph relationships.

# PART 8: HYBRID RETRIEVAL

## 7. Combine all three retrieval mechanisms

This is the central retrieval component of Increment 4.

Use:

1. Graph RAG.
2. BM25.
3. Vector Search.

Each retrieval method provides a different type of information.

| Retrieval | Purpose |
|---|---|
| Graph RAG | Structural code relationships |
| BM25 | Exact identifiers and keywords |
| Vector Search | Semantic code relevance |

### Example

User asks:

"Where does the application handle unsuccessful payments, and which components depend on that logic?"

Possible retrieval results:

**Graph RAG**
- `Checkout → process_payment`
- `process_payment → validate_payment`

**BM25**
- `PaymentDeclinedError`
- `process_payment`
- `log_failure`

**Vector Search**
- Payment failure exception handling.
- Failed transaction response generation.
- Error logging implementation.

The results must be combined into a unified evidence collection.

### Result fusion

Use Reciprocal Rank Fusion (RRF) as the initial fusion strategy.

Formula:

RRF(d) = Σ 1 / (k + rank(d))

Where:
- d is a retrieved document or code chunk.
- k is a smoothing constant.
- rank(d) is the document's position in a retrieval result list.

Requirements:

- Deduplicate chunks.
- Preserve their source metadata.
- Preserve which retrieval methods found each chunk.
- Combine rankings.
- Return the most relevant evidence.

Do not directly add raw BM25 and vector similarity scores without considering their different scoring scales.

# PART 11: EVIDENCE-BASED CLAIM VERIFICATION

## 10. Implement answer verification

The generated answer must be checked against retrieved repository evidence.

Example generated answer:

1. `process_payment()` calls `validate_payment()`.
2. Payment failures are logged using `log_failure()`.
3. The application uses Stripe for all transactions.

Suppose the retrieved evidence supports claims 1 and 2 but does not establish claim 3.

The verifier must flag claim 3 as unsupported.

Implement verification statuses such as:

- Supported.
- Partially supported.
- Unsupported.

Possible workflow:

1. Generate answer.
2. Extract important factual claims.
3. Compare claims with retrieved evidence.
4. Identify unsupported claims.
5. Retry retrieval or generation when useful.
6. Return a corrected answer with appropriate qualifications.

Do not treat LLM confidence alone as proof.

Limit retry attempts to prevent infinite loops.

If evidence remains insufficient, clearly communicate that limitation rather than fabricating an answer.
