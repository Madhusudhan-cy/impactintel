# Additional Production Requirement: Real GitHub Authentication and User-Owned Repositories

ImpactIntel must work as a real multi-user GitHub-integrated application.

Currently, the deployed Repository Selection page appears to show existing project/sample repository behavior and reports a 404 when loading repositories.

I do NOT want production users to see hardcoded sample repositories or repositories bundled with the ImpactIntel source project.

## 1. Landing page authentication

When a user clicks "Continue with GitHub":

- Redirect them to the backend GitHub authorization endpoint.
- Start the actual GitHub OAuth/user authorization flow.
- Validate OAuth state.
- Authenticate the actual GitHub user.
- Create a secure application session.
- Return the user to ImpactIntel after successful authentication.

If the user is not authenticated and opens a protected route such as /repositories, redirect them to GitHub login rather than displaying sample repositories.

## 2. GitHub App installation

After user authentication:

- Check whether the GitHub App is installed on an account accessible to that user.
- If no suitable installation exists, redirect the user to the GitHub App installation page.
- Allow installation on their personal GitHub account or an organization where they have permission.
- Allow selection of all or selected repositories according to GitHub App installation settings.
- After installation, retrieve the installation ID and establish the correct user-to-installation relationship.

Do not confuse GitHub user authentication with GitHub App installation authorization. They are separate steps.

## 3. Repository listing

The Repository Selection page must display actual repositories accessible through the authenticated user's authorized GitHub App installation.

Requirements:

- Fetch repository data from GitHub through the backend.
- Display repository owner, name, visibility, default branch and language where available.
- Support pagination.
- Support repository search.
- Show useful loading, empty and error states.
- Refresh repository data when requested.
- Never expose GitHub installation access tokens or private keys to React.

Do not use hardcoded sample repository data in production.

## 4. Remove development bypass from production

Inspect the existing local development authentication bypass.

The browser currently reports:
"Using local dev bypass: Error: Not Found"

Ensure:

- Development bypass is available only in local development when explicitly enabled.
- Production builds never activate the bypass.
- Production authentication failures are handled properly.
- Do not silently substitute sample repositories when the GitHub API fails.
- Show a clear authentication or repository-access error instead.

## 5. Repository selection and indexing

When the user selects a repository:

- Validate that the authenticated user has access through the GitHub App installation.
- Use the actual owner and repository name.
- Retrieve source from the authorized GitHub repository.
- Index the selected repository using the existing remote ingestion implementation.
- Store graph data and analysis records separately for each repository.
- Record the actual branch and commit SHA.
- Never use the sample repository as a fallback.

## 6. Multi-user isolation and security

- Every repository must be associated with its GitHub owner, installation and authorized application user context.
- A user must not access another user's private repository data without authorization.
- Validate repository access on the backend for every relevant operation.
- Keep GitHub App private keys and installation tokens backend-only.
- Use secure session handling.
- Do not bypass authentication to make repository loading work.

## 7. Existing functionality

Preserve the existing:
- FastAPI backend.
- React frontend.
- GitHub App integration.
- Repository indexing.
- NetworkX graph construction.
- PR impact analysis.
- PostgreSQL persistence.
- Prathiksha assistant.
- Existing UI design.

Do not rebuild the project.

## 8. Fix the current deployment error

Also diagnose the existing 404:

GET https://impactintel.onrender.com/repos

Inspect frontend API URL construction and actual FastAPI route registration. Fix the API prefix mismatch consistently across all API modules.

## 9. Testing

Test these production scenarios:

1. Unauthenticated visitor clicks Continue with GitHub.
2. GitHub login succeeds.
3. User without a GitHub App installation is prompted to install it.
4. User with an installation sees their authorized repositories.
5. User selects a repository and starts indexing.
6. User refreshes the page and their session is handled correctly.
7. An unauthenticated visitor cannot access protected repository pages.
8. The application never displays bundled sample repositories as the authenticated user's repositories.

Report the files changed, actual endpoints used, tests executed and any GitHub App configuration still required.

Implement only after inspecting the existing architecture. Do not replace real GitHub authentication with mocks.
