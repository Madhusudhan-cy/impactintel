`Checkout.jsx → PaymentService.js`

Increment 3 improves the Code Knowledge Graph by extracting finer-grained code relationships.

**Main objective: Extend the existing graph from file-level dependencies to function-level, class-level, component-level, API-level, and test-level relationships.**

# 5. JAVASCRIPT/TYPESCRIPT ADVANCED EXTRACTION

Improve the existing Tree-sitter extractor.

Implement the following capabilities.

## 5.1 Function extraction

Identify:

- Function declarations.
- Arrow functions.
- Function expressions.
- Exported functions.
- Async functions.
- Class methods.
- Methods inside supported object structures.

Example:

```javascript
export async function processPayment() {
    validatePayment();
    chargeGateway();
}
```

Expected extraction:

- Function node: `processPayment`
- Function node: `validatePayment` reference
- Function node: `chargeGateway` reference
- `defines` relationship from file to defined function.
- `calls` relationships from processPayment to the resolved callees where possible.

Do not invent call targets.

## 5.2 Class extraction

Identify:

- Class declarations.
- Class methods.
- Inheritance where supported.
- Methods belonging to classes.

Example:

```javascript
class PaymentService {
    validatePayment() {}

    processPayment() {
        this.validatePayment();
    }
}
```

Expected relationships:

- File defines PaymentService.
- PaymentService defines its methods.
- processPayment calls validatePayment.

Handle `this.method()` references where they can be resolved reliably.

## 5.3 Function call extraction

Identify function calls inside supported JavaScript/TypeScript code.

Examples:

```javascript
processPayment();
```

```javascript
paymentService.processPayment();
```

```javascript
this.validatePayment();
```

Resolve calls using:

- Local function definitions.
- Imported symbols.
- Class and method context.
- Module scope where possible.

Important limitations:

Dynamic dispatch, reflection, callbacks, dependency injection, and ambiguous method calls may not be statically resolvable.

If a call cannot be resolved reliably, record it as unresolved or ambiguous rather than creating a false relationship.

## 5.4 Import and export resolution

Improve the existing import resolution to support:

- Named imports.
- Default imports.
- Namespace imports where practical.
- Re-exports where practical.
- Relative paths.
- Supported file extensions.
- Index-file conventions.

Preserve existing functionality.

# 11. UPDATE IMPACT ANALYSIS

The current impact engine performs reverse dependency traversal using file-level dependencies.

Extend it to take advantage of finer-grained relationships.

Examples:

- If a function changes, identify functions that call it.
- Identify components that depend on those functions.
- Identify related API routes.
- Identify tests linked to affected code.
- If a React component changes, identify components that render it.

Important graph direction:

Store dependency relationships as:

`Dependent → Dependency`

For example:

`Checkout → processPayment`

`processPayment → validatePayment`

If `validatePayment` changes, reverse traversal identifies its dependents.

## Impact traversal rules

- Preserve the maximum three dependency levels.
- The changed entity is depth 0.
- Direct dependents are depth 1.
- Indirect dependents are depth 2 and depth 3.
- Test relationships must not consume the three-level dependency traversal limit.
- Return closest affected entities first.
- Preserve dependency paths and evidence.
- Handle cycles safely.
- Support multiple changed files and symbols.
- Do not report unrelated entities.

If function-level mapping is unavailable for a PR change, fall back to file-level analysis.

Clearly indicate which analysis level was used.

Do not claim function-level impact for a file-only result.
